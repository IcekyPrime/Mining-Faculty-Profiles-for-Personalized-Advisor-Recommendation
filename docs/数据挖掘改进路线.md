# 数据挖掘层面的改进路线（v1.9 合并版 → v2.7 续修）

这份文档回答两个问题：

1. 现有项目已经用到了哪些数据挖掘/信息检索技术？
2. 在不削减现有功能、不改评分权重的前提下，下一步还能怎么改进？

## 1. 现有处理层与检索层

| 环节 | 现有做法 | 代码位置 |
| --- | --- | --- |
| 文本表示 | jieba 分词 + TF-IDF，领域词表/停用词 | `processing/keyword_extract.py` |
| 近似相似 | Shingling + MinHash + LSH，Jaccard 阈值 | `processing/similarity_index.py` |
| 链接分析 | 合作网络 PageRank / HITS | `processing/ranking.py` |
| 社区发现 | kNN 相似图 + Louvain | `processing/community.py` |
| 聚类 | 研究方向 K-means，K=8 | `processing/clustering.py` |
| 关联规则 | Apriori（课程—方向/荣誉） | `processing/association.py` |
| 综合评分 | v1 等权分位数 + v2 可用维度归一/收缩 | `processing/score.py`、`score_v2.py` |
| 关键词检索 | 姓名 > 拼音 > 关键词 > 方向 > 研究所 > 职称的多级子串规则 | `app/services.py: relevance()` |

这套处理层已经覆盖课程中的文本、相似度、图算法、聚类和关联规则，但**检索排序长期只有人工规则**，
缺少可复现的离线评估；这是本轮最先补的缺口。

## 2. 本轮已落地的改进

### 2.1 BM25F 检索基线（已实现）

新增 `app/retrieval.py`：

- 中文按「单字 + 相邻二元组」切分，英文/数字按词切分；
- 姓名、拼音、关键词、研究方向、研究所、职称使用不同字段权重（BM25F 简化版）；
- IDF 使用 `log(1 + (N - df + 0.5) / (df + 0.5))`，负值截断；
- 只在 `sort=bm25` 时生效，旧 `score/score2/academic/teaching/relevance` 完全不变；
- 索引按数据库 `(path, mtime, size)` 缓存，补录/重跑处理层后自动失效；
- `df` 按教师文档去重（同一词同时出现在姓名/关键词/方向时只计一次），
  修正后 10 条离线查询的平均 NDCG@10 从 0.782 升到 0.794；
- 搜索结果新增 `bm25` 字段，保留原有的 `relevance` 字段，旧调用方不受影响。

前端在 AI 查询页和导师名录页各增加一个 `BM25` 排序按钮，两套排序状态独立保存。

### 2.2 离线评估（已实现）

新增：

- `docs/eval/queries.json`：10 个研究方向查询 + 人工核对的相关教师 ID；
- `scripts/evaluate_retrieval.py`：比较规则相关度与 BM25F 的 NDCG@10、MAP@10、HitRate@10、P@5；
- `docs/eval/results.md`：自动生成的评估结果。

运行：

```bash
python scripts/evaluate_retrieval.py
```

本轮结果（摘要）：

| 方法 | 平均 NDCG@10 | 平均 MAP@10 | 平均 HitRate@10 | 平均 P@5 |
| --- | ---: | ---: | ---: | ---: |
| 规则相关度 | 0.959 | 0.938 | 1.000 | 0.940 |
| BM25F | 0.794 | 0.709 | 1.000 | 0.700 |

**如何解读**：标签是按“研究方向中包含完整查询短语”人工标注的，规则方法天然占优；
BM25 会命中词项相同但主题更分散的档案。因此这组数字说明的是「标签口径会强烈影响结论」，
而不是「BM25 一定更差」。下一步应补充语义相关性标注（同一方向的不同表述、近义词），
再用 NDCG 比较；这也是信息检索实验里常见的标注偏差问题。

### 2.3 不扩充数据的检索增强（本轮新增）

数据量无法继续增加，因此这一轮只使用现有 773 位教师、13,088 篇论文和 1,663 条课程记录：

| 改动 | 做法 | 结果/取舍 |
| --- | --- | --- |
| 查询缩写扩展 | 第二轮先写死 `ML→机器学习`、`CV→计算机视觉` 等；第三轮改为 `data/mining/lexicon.json` + 语料自学习 | 现有 10 条中文查询的 BM25F 保持 0.794；`ML`、`CV` 查询能召回库内中文关键词；换领域不用改代码 |
| 简介字段实验 | 曾把 `bio` 以 0.8 权重加入 BM25F 字段 | 10 条查询 NDCG 从 0.794 降到 0.668；简介里的任职/项目词造成噪声，**已回退**，简介继续只在对话 RAG 中使用 |
| 对话姓名索引 | `assistant/rag.py` 增加 `name` 字段，避免问“朱燕民”时只能靠方向/关键词碰运气 | 姓名问题稳定命中本人 |
| Graph RAG 合作者召回 | 普通查询只给已有词法命中的合作者加权；明确问“合作者/团队/实验室”时，从种子教师沿合作边新增最多 2 个高权重邻居 | “朱燕民 合作者”能返回其合作者，并带 `graph_reason`，不再只做“已有命中的重排” |

**为什么不做中文同义词全量扩展**：试过把“计算机视觉→图像处理”“机器人→具身智能”等中文同义词全部加入，
NDCG 反而降到 0.682。原因是现有标签按研究方向原词标注，泛化词会拉进主题更散的档案。
因此只保留“缩写→库内标准写法”这类低歧义扩展。

### 2.4 同类项目调研与「数据工坊」（本轮新增）

为了避免把 LLM 直接塞进数据入口，本轮先调研了公开的数据准备/清洗项目，抽取可复用的工程范式：

| 项目 | 关键做法 | 对本项目的映射 |
| --- | --- | --- |
| `tidycsv` | 浏览器内确定性 CSV/Excel 清洗，同输入同输出，不依赖 LLM | 规则清洗引擎独立于 AI，可单独完成 |
| `sheets-cleaner` | 写入前报告、预览、显式确认 | 预览任务 token + 质量报告 + 确认入库 |
| `arnio` | C++ 数据准备、schema validation、profiling | 表头别名、字段类型/范围校验、缺失率 |
| `vscode-data-wrangler` | 每个清洗操作可回溯，并预览生成的 Pandas 代码 | 行级 `changes` 记录清洗前后差异 |
| `pointblank` | 验证计划与失败行报告 | 行级 `issues`、错误/警告分离、失败行可导出 |
| `GABRIEL` | 把 classify / extract / merge 等操作封装为 LLM 数据算子 | AI 只作为可选算子，不接管写库 |
| `galactic` | AI 分类、AI column、去重与蒸馏 | AI 辅助实体分类与列规范化 |
| `CleanAgent` | LLM 做列类型标注、生成标准化代码 | 模型负责建议，规则负责验证与执行 |

共同结论：**先预览后写入、规则与质量校验分离、重复/异常检测显式化、AI 只做辅助分类或标准化、保留审计记录**。据此新增 `docs/数据工坊-导入与清洗.md`、`app/import_engine.py`、`app/import_store.py`、`app/import_ai.py`、`app/import_api.py` 和独立 `/workspace` 页面；没有改动原三功能区布局，也没有改 `score/score2` 权重。

数据工坊覆盖的数据挖掘环节：

- 数据接入与 schema 对齐（表头别名、类型转换）；
- 数据清洗与缺失/异常检测（占位值、邮箱、URL、年份、评分、列表字段）；
- 实体分类（教师 / 论文 / 课程，字段证据打分）；
- 去重与实体消歧的轻量规则（姓名+学院、DOI、教师+课程代码）；
- 质量评分与行级审计；
- 受控写入与处理层刷新；
- AI/本地 Qwen 只做辅助复核，输出经过白名单过滤与规则重校验；
- 写库入口的工程约束：非空行号选择、原子申请写库权、无变更不排队处理层，避免误全量写入和并发重复入库。

### 2.5 移动端 AI 助手（v1.9.1 融入，v2.7 同步加固）

对比 `AdvisorFinder-mobile.apk.1` 后发现，APK 比副本原移动端多出“底部 AI 抽屉 + AI 服务配置”。
其实现不是端侧 Qwen：没有 wllama 库和模型权重，而是离线规则意图识别 + 教师库 RAG + 可选
OpenAI 兼容 API。合入后保留“本地优先、证据可追溯、模型失败回退规则”的思路，并补了
URL 协议白名单、远程 HTTPS、本机端点免 Key、请求超时、真实连接状态、语言切换重翻译、
`res/raw/web_ai` 兜底。v2.7 同步后版本为 `versionCode 18 / versionName 2.7`，并补入
英文/拼音姓名检索、抽屉滚动复位、输入框失焦与 `lostpointercapture` 修复；移动静态数据
更新为 773 位教师、13,092 篇论文。本轮再把 `ML/CV/NLP/LLM/GNN/FL` 等缩写并入移动端
alias 表，并对 1–4 位短英文启用词边界匹配，避免 `html` 命中 `ml`、`said` 命中 `ai`。

GitHub v1.9 本身没有引入模型做数据清洗：`app/` 只有单体 Flask 与统计/检索路由，清洗仍是
`processing/preprocess.py` 的正则、拼音索引、作者抽取与合作网络；模型清洗只存在于副本的
数据工坊，且默认关闭、只做辅助复核。

详见 `docs/移动端-AI助手与打包.md`。

### 2.6 可泛化的挖掘组件（第三轮新增）

针对“不能只对当前数据有效”的要求，把写死规则改为外置配置 + 语料自学习：

| 组件 | 实现 | 泛化点 |
|---|---|---|
| 查询扩展 | `app/mining.py` + `data/mining/lexicon.json` | 词典可换；从“中文（ML）”模式自动学习缩写 |
| 主题模型 | `processing/topic_model.py` | TF-IDF + NMF；K 由语料规模与轮廓系数决定 |
| 主题排序 | `app/api.py`、`app/services.py` | `sort=topic` 在 BM25 召回集内 0.6/0.4 融合 |
| 自动聚类 | `processing/clustering.py` | SVD 50 维 + K-means + 轮廓系数，K 不再固定 8 |
| 关联规则 | `processing/association.py` | 词典 `areas` 优先，缺失时用当前语料 TF-IDF 高频词 |
| 对话 RAG | `assistant/rag.py` | 外置词典叠加 + 语料缩写学习 |

当前结果：主题 K=8、771 篇文档、词表 1,304；聚类轮廓系数 0.0754；关联规则 5 条；
`sort=topic` 的 NDCG@10 为 0.798（BM25F 0.768，纯主题 0.097），MAP@10 0.703。
公式、参数与换数据步骤见 [`数据挖掘-算法与泛化说明.md`](数据挖掘-算法与泛化说明.md)。

## 3. 下一阶段可落地的改进（按投入排序）

### P0：混合检索与查询扩展（部分已落地）

- 已落地：外置词典、语料自学习缩写、BM25 + 主题 0.6/0.4 混合；
- 仍待做：把字段权重提到配置文件、设置页可调；扩到 30–50 条标注查询；
- RRF 仍可作为第二种融合方案对比，但当前 10 条查询不足以证明它优于线性融合。

### P1：语义向量检索（3–5 天，课程展示价值高）

- 用 `BGE-M3` / `text2vec` 对「姓名 + 方向 + 关键词 + 简介」编码；
- 用 FAISS/Chroma 建索引，和 BM25 做 hybrid + RRF；
- 冷启动可用 `sentence-transformers` 的小模型，离线缓存向量到 `data/exports/embeddings.npy`；
- 评估仍用 `scripts/evaluate_retrieval.py`，把新排序器注册进去即可。

注意：这是**新增检索通道**，不替换原有规则排序；设置页提供“规则 / BM25 / 语义 / 混合”开关。

### P2：研究者主题相似度（轻量版已落地）

- 已落地：TF-IDF + NMF 的教师-主题分布，档案页与洞察页可看 `topic_label`；
- 仍待做：用论文标题/摘要替代教师简介、用 Jensen–Shannon 散度补“主题相似导师”；
- BERTopic/神经主题模型作为后续方案，不替换现有可复现的 NMF 基线。

### P3：合作网络链接预测（3–5 天）

- 现有合作网络覆盖 676 人（2,347 条边），继续做**实体消歧**（同名/缩写/机构），
- 用共作者图做 Adamic-Adar、资源分配或 TransE/DistMult 链接预测；
- 输出「潜在合作者」而不是直接断言合作，避免把预测当事实。

### P4：聚类质量与公平性（自动 K 已落地）

- 已落地：SVD 50 维 + K-means + 轮廓系数自动选 K；轮廓系数从高维稀疏的 0.020 提升到 0.0754；
- 仍待做：Calinski-Harabasz 对照、Louvain 超大社区检查、学院/职称曝光公平性审计。

## 4. 不建议现在做的事

- **不要先改 score/score2 权重**：用户明确要求权重暂不动；排序实验应作为独立通道；
- **不要用 LLM 直接给导师打分**：不可复现、成本高，且容易把“网页描述”当事实；
- **不要在没有标注集时宣称某算法更好**：先把评估协议固定，再比较。
